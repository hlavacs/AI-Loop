Complete Worker System
======================

The system is a small Claude + Codex development loop with durable state in SQLite and activation messages in Redis Streams.

Main Components
---------------

start_job.py
Creates a job. Job ids use the form JYYYYMMDD-HHMMSS-ffffff. Before submitting the job, it stages and commits all current changes in the target repo with a message like "AI loop snapshot before job <job_id>" when there is anything to commit. It then writes the job to SQLite, optionally creates a Git worktree and branch, overlays any remaining checkout changes into the worktree, and sends a PLAN message to Redis stream ai:claude:requests.

claude_controller.py
Acts as planner/reviewer. It consumes PLAN and REVIEW messages from ai:claude:requests. For PLAN, it creates one tiny Codex tasklet. For REVIEW, it inspects Codex output, test output, git diff, and job history, then decides CONTINUE, REPAIR, DONE, or HUMAN_NEEDED. Task ids use the form TYYYYMMDD-HHMMSS-ffffff. On DONE, it promotes the successful worktree changes back to the target repo before marking the job done.

codex_worker.py
Acts as implementation worker. It consumes tasks from ai:codex:tasks, runs codex exec in the job worktree, runs the task's test command, captures git status/diff/output, writes a run record to SQLite, then sends a REVIEW request back to Claude.

watcher.py
Watches terminal streams: ai:done, ai:human, and ai:dead. It prints final outcomes and errors.

Storage
-------

ai_loop.sqlite3
Durable database. It stores jobs, tasks, runs, Claude decisions, and events.

Tables:
- jobs: overall job goal, repo/worktree paths, status, history
- tasks: individual Codex tasks
- runs: Codex execution results, test output, git diff
- decisions: Claude planning/review decisions
- events: audit trail

Message Queue
-------------

Redis Streams are used for coordination:

ai:claude:requests  PLAN and REVIEW messages for Claude
ai:codex:tasks      implementation tasks for Codex
ai:done             completed jobs
ai:human            jobs needing human intervention
ai:dead             worker/controller failures

Flow
----

1. User creates a job with job.bash or start_job.py.
2. start_job.py commits all current target repo changes if needed.
3. Job is stored in SQLite.
4. PLAN is queued on ai:claude:requests.
5. Claude controller creates the first tiny tasklet.
6. Task is stored in SQLite and queued on ai:codex:tasks.
7. Codex worker runs the task in the worktree.
8. Worker stores run output, tests, git status, diff.
9. Worker queues REVIEW for Claude.
10. Claude decides:
   - CONTINUE: create next task
   - REPAIR: create corrective task
   - DONE: promote worktree changes to the target repo, then publish to ai:done
   - HUMAN_NEEDED: publish to ai:human

Promotion
---------

Successful jobs are not left only in /Users/hlavacs/GitHub/ai-runs/<job_id>. When Claude returns DONE, claude_controller.py reads git status in the job worktree and copies changed, untracked, and deleted paths back to the original repo_path.

If the target repo already has local changes in the same promoted paths, promotion is rejected. The controller records promotion_failed and marks the job human_needed instead of overwriting local work. When promotion succeeds, it records promotion_completed and then marks the job done.

This means a completed job that creates PLAN.md should leave the promoted copy at:

/Users/hlavacs/GitHub/ViennaVulkanEngine/PLAN.md

Git Worktrees
-------------

Jobs normally run in isolated Git worktrees under:

/Users/hlavacs/GitHub/ai-runs/<job_id>

The main repo tracks these linked worktrees through Git metadata. Use remove_ai_worktrees.bash to clean them up instead of deleting folders manually.

Run Scripts
-----------

loopctl.bash
Controls the loop processes in the background. Supported commands:

./loopctl.bash start
./loopctl.bash stop
./loopctl.bash restart
./loopctl.bash status

It starts the Claude controller, Codex worker, and watcher through the wrapper scripts. It stores PID files in ./run by default, or in AI_LOOP_RUNTIME_DIR if set. It can also detect direct python claude_controller.py, codex_worker.py, and watcher.py processes when reporting status or stopping.

run_claude.bash
Starts the Claude controller. It appends stdout/stderr to ./logs/claude_controller.log by default, or AI_LOOP_LOG_DIR/claude_controller.log if AI_LOOP_LOG_DIR is set.

run_codex.bash
Starts the Codex worker with sandbox bypass enabled by default. It appends stdout/stderr to ./logs/codex_worker.log by default, or AI_LOOP_LOG_DIR/codex_worker.log if AI_LOOP_LOG_DIR is set.

run_watcher.bash
Starts terminal event watcher. It appends stdout/stderr to ./logs/watcher.log by default, or AI_LOOP_LOG_DIR/watcher.log if AI_LOOP_LOG_DIR is set.

Log and Status Helpers
----------------------

print_log.bash
Prints durable SQLite history and tails process log files:

./print_log.bash
./print_log.bash --job <job_id> --limit 50
./print_log.bash --job <job_id> --limit 50 --no-process-logs

It reads jobs, runs, decisions, and events from ai_loop.sqlite3, then tails ./logs/*.log unless --no-process-logs is supplied.

clear_log.bash
Clears log-like history while keeping job/task records:

./clear_log.bash --dry-run
./clear_log.bash --yes

It deletes rows from runs, decisions, and events, and truncates ./logs/*.log. It does not delete jobs or tasks.

check_job.bash
Checks whether jobs exist and prints job status, latest task diagnostics, and active job details:

./check_job.bash
./check_job.bash <job_id>

watch_job.bash
Periodically refreshes the active job state with compact, itemized status output:

./watch_job.bash

It auto-selects the newest active job. AI_LOOP_WATCH_INTERVAL controls the refresh interval and AI_LOOP_WATCH_LOG_LIMIT controls the number of log entries.

resume_job.bash
Resumes the newest human_needed job without parameters:

./resume_job.bash

It uses AI_LOOP_RESUME_MAX_ITERATIONS, defaulting to 1000.

remove_ai_worktrees.bash
Removes registered AI worktrees under /Users/hlavacs/GitHub/ai-runs and deletes leftover job folders:

./remove_ai_worktrees.bash

Force removal is enabled by default. Set AI_LOOP_FORCE_REMOVE_WORKTREES=0 to ask Git to refuse dirty worktrees.

clear_db.bash
Clears the full database, including jobs and tasks:

./clear_db.bash --dry-run
./clear_db.bash --yes

Important Detail
----------------

run_codex.bash sets CODEX_BYPASS_SANDBOX=1 by default.

That means Codex runs with --dangerously-bypass-approvals-and-sandbox unless overridden:

CODEX_BYPASS_SANDBOX=0 ./run_codex.bash

Jobs and tasklets are intentionally small. Claude should create many precise tasklets instead of broad mixed tasks. Each status line includes a counter and a short same-line description so progress can be read immediately.

Operational Proof
-----------------

To prove the loop is up:

./loopctl.bash status
./print_log.bash --limit 50

A healthy status shows:

claude_controller running pid=<pid>
codex_worker running pid=<pid>
watcher running pid=<pid>

To prove end-to-end behavior, create a small throwaway Git repo, start the loop with ./loopctl.bash start, submit a job with start_job.py, and check that:

- ./check_job.bash shows the job progressing or done
- ./print_log.bash shows controller/worker/watcher activity
- the job worktree contains the requested change
- the target repo contains the promoted change after DONE
- the configured test command passes
