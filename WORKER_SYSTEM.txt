Complete Worker System
======================

The system is a small Claude + Codex development loop with durable state in SQLite and activation messages in Redis Streams.

Fresh Machine Dependencies
--------------------------

ai-loop itself is project-agnostic. A fresh machine needs the loop runtime tools plus whatever build/test tools the target project requires.

Common required software:
- Git, including git worktree support
- Python 3.10 or newer
- Python venv and pip support
- redis-py Python package
- Redis server
- Bash
- Claude CLI, available as claude
- Codex CLI, available as codex or configured with CODEX_BIN
- Standard command-line utilities such as awk, sed, find, tail, and chmod

Ubuntu setup:

sudo apt update
sudo apt install -y git python3 python3-venv python3-pip redis-server bash coreutils findutils gawk sed procps ca-certificates curl build-essential

Then create or refresh the ai-loop Python environment:

python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install redis

Start Redis, or enable it as a service:

redis-server --save "" --appendonly no

or:

sudo systemctl enable --now redis-server

macOS setup:

xcode-select --install

Install Homebrew if it is not already installed, then:

brew install git python redis bash coreutils gawk gnu-sed

Then create or refresh the ai-loop Python environment:

python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install redis

Start Redis for the current shell:

redis-server --save "" --appendonly no

or start it as a Homebrew service:

brew services start redis

Claude CLI and Codex CLI should be installed and authenticated according to their current vendor instructions. Verify them before starting the loop:

claude --version
codex --version
redis-cli ping

Target project dependencies are separate. For example, a C++ project may need CMake, Ninja, a compiler, Vulkan SDK, or vcpkg; a JavaScript project may need Node.js and npm; a Python project may need pytest and project-specific packages. The job's test command must use the target project's actual test runner.

Main Components
---------------

start_job.py
Creates a job. Job ids use the form JYYYYMMDD-HHMMSS-ffffff. Before submitting the job, it stages and commits all current changes in the target repo with a message like "AI loop snapshot before job <job_id>" when there is anything to commit. It then writes the job to SQLite, optionally creates a Git worktree and branch, overlays any remaining checkout changes into the worktree, and sends a PLAN message to Redis stream ai:claude:requests. The default maximum iteration count is 50000. If no test command is supplied, it infers a generic project command: CMake presets first, then plain CMake, then npm test, then pytest for Python projects, and finally true when no known runner is detected.

claude_controller.py
Acts as planner/reviewer. It consumes PLAN and REVIEW messages from ai:claude:requests. For PLAN, it creates one tiny Codex tasklet. For REVIEW, it inspects Codex output, test output, git diff, job history, code quality, project guideline compliance, local architecture/style patterns, scope control, maintainability, and proportional test coverage, then decides CONTINUE, REPAIR, DONE, or HUMAN_NEEDED. HUMAN_NEEDED is a last resort: Claude should first analyze the blocker, identify solution paths, and choose REPAIR whenever a safe automated diagnostic or fix exists. Task ids use the form TYYYYMMDD-HHMMSS-ffffff. The controller stores the job's current test command on each new task; Claude may discuss tests in its JSON, but the persisted validation command is the job-level command. If Claude echoes stale test acceptance text from an earlier command, the controller replaces it with the current job test command. On DONE, it promotes the successful worktree changes back to the target repo before marking the job done.

codex_worker.py
Acts as implementation worker. It consumes tasks from ai:codex:tasks, runs codex exec in the job worktree, re-reads the task row immediately before validation, runs the current task test command, captures git status/diff/output, writes a run record to SQLite, then sends a REVIEW request back to Claude. The captured diff includes untracked new files so Claude can review newly created code. Git porcelain output is parsed without stripping significant leading spaces, so changed-file paths remain accurate. Codex should follow project instruction files when present, but missing instruction files such as AGENTS.md are not a blocker unless the job explicitly requires them. If the original job text mentions file-like guidance paths, Codex is given the currently existing paths and must re-read them at task start.

watcher.py
Watches terminal streams: ai:done, ai:human, and ai:dead. It prints final outcomes and errors.

Storage
-------

ai_loop.sqlite3
Durable database. It stores jobs, tasks, runs, Claude decisions, and events.

Tables:
- jobs: overall job goal, repo/worktree paths, status, history
- tasks: individual Codex tasks
- runs: Codex execution results, test output, git diff
- decisions: Claude planning/review decisions
- events: audit trail

Message Queue
-------------

Redis Streams are used for coordination:

ai:claude:requests  PLAN and REVIEW messages for Claude
ai:codex:tasks      implementation tasks for Codex
ai:done             completed jobs
ai:human            jobs needing human intervention
ai:dead             worker/controller failures

Flow
----

1. User creates a job with ai_job.bash or start_job.py.
2. start_job.py commits all current target repo changes if needed.
3. Job is stored in SQLite.
4. PLAN is queued on ai:claude:requests.
5. Claude controller creates the first tiny tasklet.
6. Task is stored in SQLite and queued on ai:codex:tasks.
7. Codex worker runs the task in the worktree.
8. Worker stores run output, tests, git status, diff.
9. Worker queues REVIEW for Claude.
10. Claude decides:
   - CONTINUE: create next task
   - REPAIR: enter fixing status and create a focused corrective task
   - DONE: promote worktree changes to the target repo, then publish to ai:done
   - HUMAN_NEEDED: publish to ai:human only when no safe automated diagnostic or fix remains

Fixing State
------------

When Claude returns REPAIR, the controller sets the job status to fixing, records the reason and task goal in the task_queued event, and prints both the problem and the concrete repair task. The worker keeps the job in fixing while Codex runs the repair. After the run, Claude reviews again: if the problem is gone it continues or finishes; if not, it should issue another narrow REPAIR task when an automated path remains.

The fixing state is used for code defects, failed tests, guideline violations, bad build wiring, fixable environment/configuration problems, recoverable promotion failures, and other blockers the loop can safely address. HUMAN_NEEDED should appear only after automated repair paths are exhausted or ruled out.

Promotion
---------

Successful jobs are not left only in the AI runs directory. When Claude returns DONE, claude_controller.py reads git status in the job worktree and copies changed, untracked, and deleted paths back to the original repo_path.

If the target repo already has local changes in the same promoted paths, promotion is rejected. The controller records promotion_failed and marks the job human_needed instead of overwriting local work. When promotion succeeds, it records promotion_completed and then marks the job done.

This means a completed job that creates PLAN.md should leave the promoted copy at:

<repo_path>/PLAN.md

Git Worktrees
-------------

Jobs normally run in isolated Git worktrees under:

<AI_LOOP_RUNS_DIR>/<job_id>

The main repo tracks these linked worktrees through Git metadata. Use ai_remove_worktrees.bash to clean them up instead of deleting folders manually.

AI-loop scripts must be project-agnostic. They must not depend on ViennaVulkanEngine, AGENTS.md, src/versions/simple, or any other target-project-specific path or file. Project instruction files are optional inputs, not ai-loop requirements.

Referenced Guidance Refresh
---------------------------

The initial job description, constraints, and acceptance criteria may name guidance files. In one project those files may be AGENTS.md; in another project they may be named differently. The loop treats these as generic file-like paths, not hardcoded project concepts.

On every Claude PLAN and REVIEW request, claude_controller.py extracts mentioned file-like paths, resolves existing files inside the job worktree, and includes a refreshed snapshot with path, modification time, size, truncation flag, and current text content. This lets Claude notice updated guidance while the job is still running and prefer current instructions over older summaries.

On every Codex task, codex_worker.py provides the current list of existing referenced guidance files and tells Codex to re-read them at task start. For long tasklets, Codex is also instructed to check modification times and re-read before finalizing when the task depends on those files.

This refresh mechanism is generic. It is triggered by mentioned file paths and existing files in the worktree, not by a hardcoded name such as AGENTS.md.

Run Scripts
-----------

ai_loopctl.bash
Controls the loop processes in the background. Supported commands:

./ai_loopctl.bash start
./ai_loopctl.bash stop
./ai_loopctl.bash restart
./ai_loopctl.bash status

It starts the Claude controller, Codex worker, and watcher through the wrapper scripts. It stores PID files in ./run by default, or in AI_LOOP_RUNTIME_DIR if set. It can also detect direct python claude_controller.py, codex_worker.py, and watcher.py processes when reporting status or stopping.

ai_run_claude.bash
Starts the Claude controller. It appends stdout/stderr to ./logs/claude_controller.log by default, or AI_LOOP_LOG_DIR/claude_controller.log if AI_LOOP_LOG_DIR is set.

ai_run_codex.bash
Starts the Codex worker with sandbox bypass enabled by default. It appends stdout/stderr to ./logs/codex_worker.log by default, or AI_LOOP_LOG_DIR/codex_worker.log if AI_LOOP_LOG_DIR is set.

ai_run_watcher.bash
Starts terminal event watcher. It appends stdout/stderr to ./logs/watcher.log by default, or AI_LOOP_LOG_DIR/watcher.log if AI_LOOP_LOG_DIR is set.

Log and Status Helpers
----------------------

ai_print_log.bash
Prints durable SQLite history, the job progress/time estimate when a job is selected, and tails process log files:

./ai_print_log.bash
./ai_print_log.bash --job <job_id> --limit 50
./ai_print_log.bash --job <job_id> --limit 50 --no-process-logs

It reads jobs, runs, decisions, and events from ai_loop.sqlite3, then tails ./logs/*.log unless --no-process-logs is supplied.

ai_clear_log.bash
Clears log-like history while keeping job/task records:

./ai_clear_log.bash --dry-run
./ai_clear_log.bash --yes

It deletes rows from runs, decisions, and events, and truncates ./logs/*.log. It does not delete jobs or tasks.

ai_check_job.bash
Checks whether jobs exist and prints job status, latest task diagnostics, active job details, a rough percent-complete estimate, and an estimated remaining time:

./ai_check_job.bash
./ai_check_job.bash <job_id>

ai_watch_job.bash
Periodically refreshes the active job state with compact, itemized status output:

./ai_watch_job.bash

It auto-selects the newest active job, including fixing jobs. AI_LOOP_WATCH_INTERVAL controls the refresh interval and AI_LOOP_WATCH_LOG_LIMIT controls the number of log entries.

ai_resume_job.bash
Resumes the newest human_needed job without parameters:

./ai_resume_job.bash

It uses AI_LOOP_RESUME_MAX_ITERATIONS, defaulting to 50000.

ai_remove_worktrees.bash
Removes registered AI worktrees under AI_LOOP_RUNS_DIR and deletes leftover job folders:

./ai_remove_worktrees.bash

By default it discovers target repos from the SQLite jobs table. Set AI_LOOP_TARGET_REPO to force a single repo. Force removal is enabled by default. Set AI_LOOP_FORCE_REMOVE_WORKTREES=0 to ask Git to refuse dirty worktrees.

ai_clear_db.bash
Clears the full database, including jobs and tasks:

./ai_clear_db.bash --dry-run
./ai_clear_db.bash --yes

Important Detail
----------------

ai_run_codex.bash sets CODEX_BYPASS_SANDBOX=1 by default.

That means Codex runs with --dangerously-bypass-approvals-and-sandbox unless overridden:

CODEX_BYPASS_SANDBOX=0 ./ai_run_codex.bash

Jobs and tasklets are intentionally small. Claude should create many precise tasklets instead of broad mixed tasks. Each status line includes a counter and a short same-line description so progress can be read immediately. Status output also includes a simple heuristic estimate of percent complete and remaining time. The estimate is based on completed runs, active queued/running work, and elapsed job time; it is intentionally approximate.

Claude review is a quality gate. It should return REPAIR when Codex visibly violates coding guidelines, ignores existing project patterns, changes unrelated behavior, leaves brittle or duplicated code without cause, omits necessary tests for risky changes, or satisfies the task only superficially. It should avoid HUMAN_NEEDED unless the remaining action truly requires a person, credentials, paid installation, physical device/display access, or a destructive choice that cannot be safely automated.

Operational Proof
-----------------

To prove the loop is up:

./ai_loopctl.bash status
./ai_print_log.bash --limit 50

A healthy status shows:

claude_controller running pid=<pid>
codex_worker running pid=<pid>
watcher running pid=<pid>

To prove end-to-end behavior, create a small throwaway Git repo, start the loop with ./ai_loopctl.bash start, submit a job with start_job.py, and check that:

- ./ai_check_job.bash shows the job progressing or done
- ./ai_print_log.bash shows controller/worker/watcher activity
- the job worktree contains the requested change
- the target repo contains the promoted change after DONE
- the configured test command passes
