++Complete Worker System
======================

The system is a small controller + worker development loop with durable state in SQLite and activation messages in Redis Streams. By default Opus plans/reviews and Codex implements, but each job can select its own controller and worker.

Fresh Machine Dependencies
--------------------------

ai-loop itself is project-agnostic. A fresh machine needs the loop runtime tools plus whatever build/test tools the target project requires.

Common required software:
- Git, including git worktree support
- Python 3.10 or newer
- Python venv and pip support
- Tkinter for the optional GUI
- redis-py Python package
- Redis server
- Bash
- Claude CLI, available as claude
- Codex CLI, available as codex or configured with CODEX_BIN
- Standard command-line utilities such as awk, sed, find, tail, and chmod

Ubuntu setup:

sudo apt update
sudo apt install -y git python3 python3-venv python3-pip python3-tk redis-server bash coreutils findutils gawk sed procps ca-certificates curl build-essential

Then create or refresh the ai-loop Python environment:

python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install redis

For the Tkinter GUI, verify:

python -m tkinter

Start Redis, or enable it as a service:

redis-server --save "" --appendonly no

or:

sudo systemctl enable --now redis-server

macOS setup:

xcode-select --install

Install Homebrew if it is not already installed, then:

brew install git python python-tk redis bash coreutils gawk gnu-sed

Then create or refresh the ai-loop Python environment:

python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install redis

For the Tkinter GUI, verify:

python -m tkinter

Start Redis for the current shell:

redis-server --save "" --appendonly no

or start it as a Homebrew service:

brew services start redis

Claude CLI and Codex CLI should be installed and authenticated according to their current vendor instructions. Verify them before starting the loop:

claude --version
codex --version
redis-cli ping

Target project dependencies are separate from ai-loop dependencies. Install whatever compiler, runtime, package manager, SDK, test framework, or external service the selected target project requires. The job's test command must use that target project's actual validation command.

Main Components
---------------

start_job.py
Creates a job. ai_job.bash can submit either ./ai_job.bash <repo-path> <job-description> or ./ai_job.bash <job-description-file>; with the one-file form it reads the file contents as the goal and uses the file's containing directory as the target repo. Job ids use the form JYYYYMMDD-HHMMSS-ffffff. By default each job gets its own selected controller, selected worker, and watcher, with per-job Redis consumer groups, PID files under ./run/jobs/<job_id>, and process logs under ./logs/jobs/<job_id>. Multiple active jobs can therefore run concurrently. Set AI_LOOP_SINGLE_ACTIVE_JOB=1 to restore the old single-active-job guard; with that guard enabled, --allow-parallel or AI_LOOP_ALLOW_PARALLEL_JOBS=1 starts another job anyway. When job creation is allowed, it stages and commits all current changes in the target repo with a message like "AI loop snapshot before job <job_id>" when there is anything to commit. It then writes the job to SQLite, optionally creates a Git worktree and branch, overlays any remaining checkout changes into the worktree, creates the job-scoped consumer groups, starts the job-scoped process trio, and sends a scoped PLAN message to Redis stream ai:claude:requests. The default maximum iteration count is 50000. With --wait, it waits indefinitely by default; pass --timeout with a positive number of seconds to impose a foreground wait limit. If no test command is supplied, it infers a generic project command: CMake presets first, then plain CMake, then npm test, then pytest for Python projects, and finally true when no known runner is detected. Each job also stores its worker and controller selection, set with --worker and --controller or the AI_LOOP_WORKER and AI_LOOP_CONTROLLER environment variables; see Worker and Controller Selection below. Default job constraints depend on the worker: capable workers (fable, opus) get "prefer coherent, self-contained tasks" constraints, while codex gets "many tiny tasklets" constraints.

claude_controller.py
Acts as planner/reviewer. It runs the job's selected controller backend: claude (Claude CLI default model or AI_LOOP_CONTROLLER_MODEL), fable, opus, or codex (codex exec --sandbox read-only --output-last-message, parsing the decision JSON from the last agent message). It consumes PLAN and REVIEW messages from ai:claude:requests. For PLAN, it creates one first task sized to the job's worker: a tiny tasklet for codex, or a larger coherent task for fable/opus. For REVIEW, it inspects worker output, test output, git diff, job history, code quality, project guideline compliance, local architecture/style patterns, scope control, maintainability, and proportional test coverage, then decides CONTINUE, REPAIR, DONE, or HUMAN_NEEDED. HUMAN_NEEDED is a last resort: Claude should first analyze the blocker, identify solution paths, and choose REPAIR whenever a safe automated diagnostic or fix exists. Task ids use the form TYYYYMMDD-HHMMSS-ffffff. The controller stores the job's current test command on each new task; Claude may discuss tests in its JSON, but the persisted validation command is the job-level command. If Claude echoes stale test acceptance text from an earlier command, the controller replaces it with the current job test command. Claude decision JSON is checked before it is accepted: the controller extracts the decision object, validates the required fields, serializes/parses it again as a round-trip guard, and if parsing or validation fails it asks Claude to remake the same decision as valid JSON only. On DONE, it promotes the successful worktree changes back to the target repo before marking the job done.

codex_worker.py
Acts as implementation worker. It consumes tasks from ai:codex:tasks and runs the job's selected worker in the job worktree: codex exec for the codex worker, or claude -p --model <model> for the fable/opus workers (with --permission-mode acceptEdits and an allowed-tools list, or --dangerously-skip-permissions when CODEX_BYPASS_SANDBOX=1). The worker prompt scales scope rules to the worker: tasklet-sized for codex, coherent multi-file tasks for fable/opus. It re-reads the task row immediately before validation, runs the current task test command, captures git status/diff/output, writes a run record to SQLite, then sends a REVIEW request back to Claude. The captured diff includes untracked new files so Claude can review newly created code. Git porcelain output is parsed without stripping significant leading spaces, so changed-file paths remain accurate. Codex should follow project instruction files when present, but missing instruction files are not a blocker unless the job explicitly requires them. If the original job text mentions file-like guidance paths, Codex is given the currently existing paths and must re-read them at task start.

When Codex needs to run a target-project executable that may crash, hang, or open a platform crash dialog, it should use ai_run_crash_safe.bash. The wrapper applies a timeout, disables core dumps where possible, and on macOS runs the executable under batch lldb when available so crashes are captured as terminal diagnostics and backtraces. A crashing target executable is treated as diagnostic input for REPAIR, not as a manual action for the user.

watcher.py
Watches terminal streams: ai:done, ai:human, and ai:dead. It prints final outcomes and errors.

ai_loop_gui.py
Provides a cross-platform Python/Tkinter GUI for normal interactive use. It does not call the bash wrappers. It creates jobs, launches claude_controller.py, codex_worker.py, and watcher.py directly as Python subprocesses, tails per-job logs, shows job/task/run/decision/event state, stops jobs, resumes paused jobs, changes controller and worker choices, starts local Redis when REDIS_URL points at localhost, clears AI worktrees, resets the database, and performs a full reset. If the active Python is missing redis-py, it creates .gui-venv, installs redis there, and restarts itself. When a job enters human_needed, the GUI shows an alert and lists practical next actions in the Overview tab. On macOS only, it can show hibernation status and select pmset hibernatemode 0, 3, or 25 with explanation strings.

Worker and Controller Selection
-------------------------------

Each job stores which implementation worker and which controller it uses.

Workers: codex (default), fable (Claude Fable via the Claude CLI; "claude" is accepted as an alias), opus (Claude Opus via the Claude CLI).
Controllers: opus (default), claude, fable, codex.

Selection, highest precedence first: --worker/--controller flags on ai_job.bash or start_job.py, then the AI_LOOP_WORKER and AI_LOOP_CONTROLLER environment variables, then the built-in defaults.

./ai_job.bash --worker fable --controller fable /path/to/repo "Implement feature X."
python3 start_job.py --worker opus --controller claude --repo /path/to/repo --goal "..."
export AI_LOOP_WORKER=fable

Models are configured with AI_LOOP_FABLE_MODEL (default claude-fable-5), AI_LOOP_OPUS_MODEL (default opus), and AI_LOOP_CONTROLLER_MODEL (default: Claude CLI default model, for the claude controller).

The fable/opus workers run:

claude -p --model "$MODEL" --permission-mode acceptEdits --allowedTools Bash,Edit,Write,MultiEdit,NotebookEdit

With CODEX_BYPASS_SANDBOX=1 they instead use --dangerously-skip-permissions. The Claude CLI has no filesystem sandbox comparable to Codex's workspace-write; Git worktree isolation is the main guardrail.

The codex controller runs codex exec --sandbox read-only --output-last-message and parses the decision JSON from the last agent message.

Task sizing follows the worker. With the codex worker, the controller plans many tiny tasklets: one narrow objective, one file cluster, a short stop point. With fable or opus workers, the controller plans larger coherent tasks that may span several related files and include their own discovery and verification, cutting controller round-trips. Default job constraints, the decision schema rules, and the worker prompt all adjust accordingly.

The database schema auto-migrates existing databases to add the worker and controller columns.

Storage
-------

ai_loop.sqlite3
Durable database. It stores jobs, tasks, runs, Claude decisions, and events.

Tables:
- jobs: overall job goal, repo/worktree paths, worker/controller selection, status, history
- tasks: individual Codex tasks
- runs: Codex execution results, test output, git diff
- decisions: Claude planning/review decisions
- events: audit trail

Message Queue
-------------

Redis Streams are used for coordination:

ai:claude:requests  PLAN and REVIEW messages for Claude
ai:codex:tasks      implementation tasks for Codex
ai:done             completed jobs
ai:human            jobs needing human intervention
ai:dead             worker/controller failures

Every Redis message payload is JSON-encoded through ai_loop/queues.py. Before a payload is published, the sender serializes it, parses it back, and rejects it if the round trip changes the value. When a receiver reads a payload, it parses and verifies that the payload is a JSON object before using it. This guards both directions of the Claude/Codex queue boundary against malformed JSON.

Flow
----

1. User creates a job with ai_job.bash or start_job.py.
2. start_job.py commits all current target repo changes if needed.
3. Job is stored in SQLite.
4. PLAN is queued on ai:claude:requests.
5. Claude controller creates the first tiny tasklet.
6. Task is stored in SQLite and queued on ai:codex:tasks.
7. Codex worker runs the task in the worktree.
8. Worker stores run output, tests, git status, diff.
9. Worker queues REVIEW for Claude.
10. Claude decides:
   - CONTINUE: create next task
   - REPAIR: enter fixing status and create a focused corrective task
   - DONE: promote worktree changes to the target repo, then publish to ai:done
   - HUMAN_NEEDED: publish to ai:human only when no safe automated diagnostic or fix remains

Fixing State
------------

When Claude returns REPAIR, the controller sets the job status to fixing, records the reason and task goal in the task_queued event, and prints both the problem and the concrete repair task. The worker keeps the job in fixing while Codex runs the repair. After the run, Claude reviews again: if the problem is gone it continues or finishes; if not, it should issue another narrow REPAIR task when an automated path remains.

The fixing state is used for code defects, failed tests, guideline violations, bad build wiring, fixable environment/configuration problems, recoverable promotion failures, and other blockers the loop can safely address. HUMAN_NEEDED should appear only after automated repair paths are exhausted or ruled out.

Transient Claude CLI transport/service failures (for example API errors, connection resets, timeouts, overloaded/rate-limit messages) are retried indefinitely inside claude_controller.py with capped exponential backoff instead of emitting HUMAN_NEEDED. The wait knobs are AI_LOOP_CLAUDE_TRANSIENT_BACKOFF_SECONDS and AI_LOOP_CLAUDE_TRANSIENT_MAX_BACKOFF_SECONDS. Missing binaries, promotion conflicts, non-transient CLI failures, and explicit Claude HUMAN_NEEDED decisions still surface to the human stream.

Executable scene or asset load errors such as "scene load failed: error=io_error" should be treated as a likely working-directory or asset-path problem first. Claude should prefer REPAIR tasks that ask Codex to reproduce from the repository/worktree root, compare the failing launch directory, inspect expected asset paths, and fix path resolution or launch documentation before considering HUMAN_NEEDED.

Promotion
---------

Successful jobs are not left only in the AI runs directory. When Claude returns DONE, claude_controller.py reads git status in the job worktree and copies changed, untracked, and deleted paths back to the original repo_path.

If the target repo already has local changes in the same promoted paths, promotion is rejected. The controller records promotion_failed and marks the job human_needed instead of overwriting local work. When promotion succeeds, it records promotion_completed and then marks the job done.

This means a completed job that creates PLAN.md should leave the promoted copy at:

<repo_path>/PLAN.md

Git Worktrees
-------------

Jobs normally run in isolated Git worktrees under:

<AI_LOOP_RUNS_DIR>/<job_id>

The main repo tracks these linked worktrees through Git metadata. Use ai_remove_worktrees.bash to clean them up instead of deleting folders manually.

AI-loop scripts must be project-agnostic. They must not depend on any concrete target repository name, instruction-file name, source directory layout, or project-specific path. Project instruction files are optional inputs, not ai-loop requirements.

Referenced Guidance Refresh
---------------------------

The initial job description, constraints, and acceptance criteria may name guidance files. Different target projects may use different names for these files. The loop treats them as generic file-like paths, not hardcoded project concepts.

On every Claude PLAN and REVIEW request, claude_controller.py extracts mentioned file-like paths, resolves existing files inside the job worktree, and includes a refreshed snapshot with path, modification time, size, truncation flag, and current text content. This lets Claude notice updated guidance while the job is still running and prefer current instructions over older summaries.

On every Codex task, codex_worker.py provides the current list of existing referenced guidance files and tells Codex to re-read them at task start. For long tasklets, Codex is also instructed to check modification times and re-read before finalizing when the task depends on those files.

This refresh mechanism is generic. It is triggered by mentioned file paths and existing files in the worktree, not by hardcoded names.

Run Scripts
-----------

All Bash scripts in the repository are listed below. Scripts are run from the ai-loop repository root unless otherwise noted.

ai_job.bash
Submits a new job through start_job.py and waits for completion. It accepts either a repo path plus inline goal text, or a single job-description file. In the file form, the file's directory is used as the repo and the file contents become the goal. It adds default constraints and acceptance criteria (sized to the selected worker), uses AI_LOOP_TEST_CMD when set, passes --worker/--controller through (defaulting from AI_LOOP_WORKER/AI_LOOP_CONTROLLER), and passes --allow-parallel when AI_LOOP_ALLOW_PARALLEL_JOBS=1.

Parameters:
./ai_job.bash [--worker codex|fable|opus] [--controller claude|fable|opus|codex] <repo-path> <job-description>
./ai_job.bash [--worker codex|fable|opus] [--controller claude|fable|opus|codex] <job-description-file>

Examples:
./ai_job.bash /path/to/project "Add FPS to the ImGui overlay."
./ai_job.bash --worker fable --controller fable /path/to/project/job.txt
AI_LOOP_TEST_CMD="ctest --test-dir build/debug" ./ai_job.bash /path/to/project "Fix the failing renderer tests."
AI_LOOP_ALLOW_PARALLEL_JOBS=1 ./ai_job.bash /path/to/project "Run an independent cleanup job."
./ai_job.bash /path/to/project/job.txt

ai_gui.bash
Starts the Tkinter GUI from the repository root. Extra arguments are passed to ai_loop_gui.py. Use --theme <name> with two leading dashes to select any installed Tk/ttk theme; -theme is not accepted. Use --list-themes to print the local theme names. The default theme keeps the current platform-native Tk style.

Parameters:
./ai_gui.bash
./ai_gui.bash --theme <theme-name>
./ai_gui.bash --list-themes

Examples:
./ai_gui.bash
./ai_gui.bash --theme clam
./ai_gui.bash --theme aqua
./ai_gui.bash --theme classic
./ai_gui.bash --list-themes

Typical macOS theme names reported by --list-themes are aqua, clam, alt, default, and classic.

ai_check_job.bash
Prints job status, updated time, task/run counts, worktree path, goal, latest task diagnostics, and a rough percent-complete/time-remaining estimate. With no job id it lists all jobs ordered by most recent update.

Parameters:
./ai_check_job.bash
./ai_check_job.bash <job_id>

Examples:
./ai_check_job.bash
./ai_check_job.bash J20260701-101500-123456
AI_LOOP_DB=/tmp/ai_loop.sqlite3 ./ai_check_job.bash

ai_clear_db.bash
Clears the full SQLite database, including jobs, tasks, runs, decisions, and events. It does not stop processes or remove worktrees by itself; use ai_reset_loop.bash or ai_loopctl.bash when process cleanup is also needed.

Parameters:
./ai_clear_db.bash --dry-run
./ai_clear_db.bash --yes

Examples:
./ai_clear_db.bash --dry-run
./ai_clear_db.bash --yes
AI_LOOP_DB=/tmp/ai_loop.sqlite3 ./ai_clear_db.bash --yes

ai_clear_log.bash
Clears log-like history while keeping job and task records. It deletes rows from runs, decisions, and events, then truncates process log files under ./logs, including nested per-job logs under ./logs/jobs/<job_id>. It supports dry-run output showing counts and log sizes.

Parameters:
./ai_clear_log.bash --dry-run
./ai_clear_log.bash --yes

Examples:
./ai_clear_log.bash --dry-run
./ai_clear_log.bash --yes
AI_LOOP_LOG_DIR=/tmp/ai-loop-logs ./ai_clear_log.bash --dry-run

ai_delete_job.bash
Deletes one job record and dependent rows from SQLite. If no job id is supplied, it deletes the newest active job in planning, queued, implementing, or fixing state. It also stops PID-file-tracked per-job controller, worker, and watcher processes for that job. It does not remove worktree folders; use ai_remove_worktrees.bash for worktree cleanup.

Parameters:
./ai_delete_job.bash
./ai_delete_job.bash <job_id>

Examples:
./ai_delete_job.bash
./ai_delete_job.bash J20260701-101500-123456

ai_hibernation.bash
macOS-only helper for reading or changing pmset hibernatemode. It is useful when long jobs should not be interrupted by sleep/hibernation policy changes. It works on macOS only. Selectable modes are 0 (disabled), 3 (enabled, default portable mode), and 25 (enabled, deep hibernation mode).

Parameters:
./ai_hibernation.bash status
./ai_hibernation.bash disable
./ai_hibernation.bash enable
./ai_hibernation.bash set <0|3|25>

Examples:
./ai_hibernation.bash status
./ai_hibernation.bash disable
./ai_hibernation.bash enable
./ai_hibernation.bash set 25

ai_loop_python.bash
Shared helper sourced by other scripts. It chooses a runnable Python interpreter, honors AI_LOOP_PYTHON, resolves Python paths, shell-quotes words, and checks that the selected Python can import redis. It is not normally run directly.

Parameters:
No command-line interface for direct use.

Examples:
source ./ai_loop_python.bash
python_bin="$(choose_ai_loop_python)"
ensure_ai_loop_python_redis "$python_bin"

ai_loopctl.bash
Controls background loop processes for operations. Normal jobs start their own per-job controller, worker, and watcher through start_job.py or resume_job.py. stop stops PID-file-tracked per-job processes first, then stops any directly launched controller, worker, or watcher processes. status reports directly launched processes and per-job PID files under ./run/jobs/<job_id>.

Parameters:
./ai_loopctl.bash stop
./ai_loopctl.bash status

Examples:
./ai_loopctl.bash stop
./ai_loopctl.bash status
AI_LOOP_RUNTIME_DIR=/tmp/ai-loop-run ./ai_loopctl.bash status

It stores PID files in ./run by default, or in AI_LOOP_RUNTIME_DIR if set. Per-job jobs use ./run/jobs/<job_id> by default.

ai_print_log.bash
Prints durable SQLite history and tails process logs. With --job, it prints the selected job's progress estimate and filters history to that job. If ./logs/jobs/<job_id> exists, --job tails that job's process logs instead of the global logs. --no-process-logs suppresses tail output.

Parameters:
./ai_print_log.bash [--job JOB_ID] [--limit N] [--no-process-logs]

Examples:
./ai_print_log.bash
./ai_print_log.bash --limit 50
./ai_print_log.bash --job J20260701-101500-123456 --limit 120
./ai_print_log.bash --job J20260701-101500-123456 --limit 50 --no-process-logs

ai_remove_worktrees.bash
Removes registered AI worktrees under AI_LOOP_RUNS_DIR and deletes leftover job folders. By default it discovers target repos from the SQLite jobs table. Set AI_LOOP_TARGET_REPO to force a single repo. Force removal is enabled by default; set AI_LOOP_FORCE_REMOVE_WORKTREES=0 to ask Git to refuse dirty worktrees.

Parameters:
./ai_remove_worktrees.bash

Examples:
./ai_remove_worktrees.bash
AI_LOOP_TARGET_REPO=/path/to/project ./ai_remove_worktrees.bash
AI_LOOP_FORCE_REMOVE_WORKTREES=0 ./ai_remove_worktrees.bash

ai_reset_loop.bash
Stops controller, worker, and watcher processes, deletes active job records, and clears the database. It does not start workers afterward because new jobs spawn their own per-job controller, worker, and watcher.

Parameters:
./ai_reset_loop.bash --dry-run
./ai_reset_loop.bash --yes

Examples:
./ai_reset_loop.bash --dry-run
./ai_reset_loop.bash --yes

ai_resume_job.bash
Resumes a paused/planning job through resume_job.py. With no arguments it picks the newest human_needed job, falling back to the newest planning job. It applies AI_LOOP_RESUME_MAX_ITERATIONS, defaulting to 50000. Extra arguments are passed to resume_job.py, so explicit job id, --goal, --constraint, --acceptance, --test-cmd, --max-iterations, --wait, --poll-interval, and --timeout are supported. Resume starts a fresh per-job controller, worker, and watcher.

Parameters:
./ai_resume_job.bash
./ai_resume_job.bash <job_id> [resume_job.py options]

Examples:
./ai_resume_job.bash
./ai_resume_job.bash J20260701-101500-123456 --constraint "Do not touch renderer setup."
./ai_resume_job.bash J20260701-101500-123456 --test-cmd "ctest --test-dir build/debug" --wait --timeout 900
AI_LOOP_RESUME_MAX_ITERATIONS=10 ./ai_resume_job.bash

ai_run_claude.bash
Starts claude_controller.py and appends stdout/stderr to ./logs/claude_controller.log, or AI_LOOP_LOG_DIR/claude_controller.log if set. When AI_LOOP_JOB_ID is set, the controller uses a job-scoped Redis consumer group, ignores messages for other jobs, and exits after that job reaches a terminal state.

Parameters:
./ai_run_claude.bash

Examples:
./ai_run_claude.bash
AI_LOOP_JOB_ID=J20260701-101500-123456 AI_LOOP_LOG_DIR=./logs/jobs/J20260701-101500-123456 AI_LOOP_RUNTIME_DIR=./run/jobs/J20260701-101500-123456 ./ai_run_claude.bash

ai_run_codex.bash
Starts codex_worker.py (which runs the job's selected worker: codex, fable, or opus) and appends stdout/stderr to ./logs/codex_worker.log, or AI_LOOP_LOG_DIR/codex_worker.log if set. It sets CODEX_BYPASS_SANDBOX=1 by default. When AI_LOOP_JOB_ID is set, the worker uses a job-scoped Redis consumer group, ignores messages for other jobs, and exits after that job reaches a terminal state.

Parameters:
./ai_run_codex.bash

Examples:
./ai_run_codex.bash
CODEX_BYPASS_SANDBOX=0 ./ai_run_codex.bash
AI_LOOP_JOB_ID=J20260701-101500-123456 AI_LOOP_LOG_DIR=./logs/jobs/J20260701-101500-123456 AI_LOOP_RUNTIME_DIR=./run/jobs/J20260701-101500-123456 ./ai_run_codex.bash

ai_run_watcher.bash
Starts watcher.py and appends stdout/stderr to ./logs/watcher.log, or AI_LOOP_LOG_DIR/watcher.log if set. When AI_LOOP_JOB_ID is set, it prints only terminal events for that job and exits after the matching event.

Parameters:
./ai_run_watcher.bash

Examples:
./ai_run_watcher.bash
AI_LOOP_JOB_ID=J20260701-101500-123456 AI_LOOP_LOG_DIR=./logs/jobs/J20260701-101500-123456 AI_LOOP_RUNTIME_DIR=./run/jobs/J20260701-101500-123456 ./ai_run_watcher.bash

ai_run_crash_safe.bash
Runs a target-project executable in a crash-safe way. It applies AI_LOOP_CRASH_SAFE_TIMEOUT or --timeout, disables core dumps where possible, and on macOS uses batch lldb when available so crashes produce terminal diagnostics and backtraces.

Parameters:
./ai_run_crash_safe.bash -- <executable> [args...]
./ai_run_crash_safe.bash --timeout 120 -- <executable> [args...]

Examples:
./ai_run_crash_safe.bash -- ./bin/debug/exe/game

ai_run_loop_proof.bash
Creates or refreshes a small C++ fixture repo, verifies its local test, submits an end-to-end proof job, waits for completion, and verifies the promoted result. It uses AI_LOOP_PROOF_REPO for the fixture path, defaulting to /tmp/ai-loop-test, and AI_LOOP_PYTHON for the Python interpreter when set.

Parameters:
./ai_run_loop_proof.bash
./ai_run_loop_proof.bash -h
./ai_run_loop_proof.bash --help

Examples:
./ai_run_loop_proof.bash
AI_LOOP_PROOF_REPO=/tmp/my-ai-loop-proof ./ai_run_loop_proof.bash

ai_watch_job.bash
Periodically refreshes the newest active job with compact status output and recent durable log entries. It auto-selects the newest planning, queued, implementing, or fixing job. AI_LOOP_WATCH_INTERVAL controls the refresh interval, defaulting to 10 seconds. AI_LOOP_WATCH_LOG_LIMIT controls the number of durable log entries, defaulting to 20.

Parameters:
./ai_watch_job.bash

Examples:
./ai_watch_job.bash

Important Detail
----------------

ai_run_codex.bash sets CODEX_BYPASS_SANDBOX=1 by default.

That means Codex runs with --dangerously-bypass-approvals-and-sandbox, and the fable/opus workers run with --dangerously-skip-permissions, unless overridden:

CODEX_BYPASS_SANDBOX=0 ./ai_run_codex.bash

Task size follows the worker. With the codex worker, jobs and tasklets are intentionally small and Claude should create many precise tasklets instead of broad mixed tasks. With fable/opus workers, the controller plans larger coherent tasks with a testable stop point. Each status line includes a counter and a short same-line description so progress can be read immediately. Status output also includes a simple heuristic estimate of percent complete and remaining time. The estimate is based on completed runs, active queued/running work, and elapsed job time; it is intentionally approximate.

Claude review is a quality gate. It should return REPAIR when the worker visibly violates coding guidelines, ignores existing project patterns, changes unrelated behavior, leaves brittle or duplicated code without cause, omits necessary tests for risky changes, or satisfies the task only superficially. It should avoid HUMAN_NEEDED unless the remaining action truly requires a person, credentials, paid installation, physical device/display access, or a destructive choice that cannot be safely automated.

Operational Proof
-----------------

To prove the loop is up:

./ai_loopctl.bash status
./ai_print_log.bash --limit 50

A healthy idle status may show no directly launched processes and no per-job processes:

claude_controller stopped
codex_worker stopped
watcher stopped
per-job processes: none

That is normal. New jobs start their own controller, worker, and watcher. While a job is active, ./ai_loopctl.bash status should show entries like:

job <job_id> claude_controller running pid=<pid>
job <job_id> codex_worker running pid=<pid>
job <job_id> watcher running pid=<pid>

To prove end-to-end behavior, run:

./ai_run_loop_proof.bash

Or create a small throwaway Git repo, submit a job with ai_job.bash or start_job.py, and check that:

- ./ai_check_job.bash shows the job progressing or done
- ./ai_print_log.bash --job <job_id> shows controller/worker/watcher activity
- the job worktree contains the requested change
- the target repo contains the promoted change after DONE
- the configured test command passes
