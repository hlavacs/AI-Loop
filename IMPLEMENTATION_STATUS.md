The path-dependent prompt regression is fixed, and promoted changes now pass the concrete validation command again from the target checkout before the job reaches `done`. Current ownership boundaries recorded before Milestone 1 changes:

- Job creation and process launch: `LoopBackend.create_job` and `LoopBackend.launch_processes` in `ai_loop_gui.py`; durable creation delegates to `ai_loop.db.create_job`.
- Controller decisions, planning/review prompts, bounded JSON remake, next-task creation, and terminal job transitions: `controller.py`.
- Worker prompt construction, task execution, test-command execution, run capture, and review handoff: `worker.py`.
- Job, task, run, controller-decision, event, and progress persistence: `ai_loop/db.py`; JSON-valued columns use the `*_json` convention with `to_json`/`from_json` conversion.

- GUI background work: `AiLoopGui._run_bg`, which performs work on daemon threads and marshals results through Tk `after` callbacks.
- Existing artifacts: worker output and diffs are stored in SQLite run rows. This checkout had no `ai_loop/artifacts.py`, `ai_loop/jobs.py`, or `ai_loop/structured_output.py` module at baseline.

Milestone 1 adds a separate service boundary and additive metadata; it does not replace or redirect the existing Quick Goal lifecycle.

### 3. AI elicitation — Complete (core + GUI diff-review/apply)

Completed core acceptance criteria:

- `ai_loop/elicitation.py` is frontend-neutral and headless. `ElicitationEngine` accepts an injected structured-output provider adapter carrying its provider/model identity and sends a portable request containing the prompt, strict schema, repository path, and mandatory read-only policy. This keeps Codex, Claude, and Gemini CLI selection/command behavior in the existing provider layer and adds no provider SDK dependency.
- The deterministic repository-analysis prompt pins the exact specification ID, version, and canonical hash; embeds the current complete document and complete result schema; prohibits repository mutation; and directs inspection of manifests, architecture, public APIs, tests, instructions, build/configuration, persistence, compatibility, and the required normal, alternate, failure, boundary, repetition, timing, pressure, numerical, and non-deterministic behavior dimensions.
- The single strict result contains a summary, complete additive `suggested_specification`, explicit decision proposals, and warnings. The existing strict specification schema is embedded under the result schema's root definitions, so every reference is internal and no external schema resolution is needed. Choice proposals require topic, question, context, two to five uniquely named options with non-empty descriptions and tradeoffs, a recommendation naming one option, and a strict boolean blocking flag.
- Runtime parsing remains authoritative. It repeats strict root/choice parsing and full `SpecificationDocument` structural/reference/path validation even when a provider claims schema enforcement. Preservation validation requires the original sequence as an exact prefix, rejects removal/reordering/merging, duplicate appended material, type changes, stable-ID changes, and changes to every non-empty user scalar. The materialized decisions array is frozen exactly; tradeoffs can only be returned as choice proposals.
- Invalid output receives exactly one structured repair request, for a hard maximum of two provider calls. Exhausted invalid analyses are recorded as failed without an artifact; provider execution failures do not enter an output-repair loop.
- Validated results are canonically serialized and stored as independently hashed immutable artifacts under `artifacts/specifications/<specification-id>/analyses/`, with analysis ID, exact source version, provider, model, status, prompt hash, canonical result JSON, artifact path/hash, application metadata, error, and timestamps in the additive `specification_analyses` table. `SpecificationService` owns artifact creation, hashing, transactional freshness checks, failure recording, loading, listing, and integrity verification. The already-present Milestone 1 `CREATE TABLE IF NOT EXISTS` migration required no destructive schema change and remains idempotent for legacy databases.
- The service repeats current-version and immutable source-hash checks while committing a validated analysis. A revision created after the provider call began produces an auditable stale record with no accepted result artifact.

### 5. Verification realization — Complete

Completed acceptance criteria:

- The iteration-8 Milestone 4 regression baseline was rerun before Milestone 5 edits with the exact required invocation `COLUMNS=1000 .gui-venv/bin/python -m pytest -q`: **253 collected, 252 passed, 1 skipped, 0 failed in 8.26s**. - `ai_loop/verification_orchestrator.py` is the focused static realization boundary. It accepts the integrity-checked compiled manifest plus job worktree and never launches a process. Each non-manual case must have a non-empty concrete command whose executable resolves; exact `auto` is rejected. The checker repeats non-empty/relative/path-traversal validation, resolves the working directory against the live worktree, rejects absolute POSIX/Windows paths and symlink escape, and requires the directory to exist.
- Declared fixtures must resolve to an existing worktree-contained path or have a deterministic generator declaration. Every declared metric must have an emitter and every required-evidence declaration must have a producer. Findings remain domain-neutral and are returned as exact missing fixture, metric, evidence, marker, command, or directory infrastructure rather than product defects.
- Bounded source discovery recognizes `AI_LOOP_CASE={"verification_id":"..."}`, `AI_LOOP_FIXTURE_GENERATOR`, `AI_LOOP_METRIC_EMITTER`, `AI_LOOP_EVIDENCE_PRODUCER`, combined `AI_LOOP_REALIZATION`, and the existing metric/evidence envelopes when colocated with a case marker. `RealizationSignals` is the equivalent external-adapter result. Discovery skips VCS metadata, virtual environments, dependency trees, immutable job artifacts, symlinks, binary files, and files over the static discovery bound.
- A resolvable broad command is never realization proof by itself. Every executable case requires its exact `AI_LOOP_CASE` marker or an equivalent adapter declaration. The checker is dry: it does not interpret an exit code, run repetitions, evaluate live metrics/assertions, or retain command output.
- `RealizationState` represents `unrealized`, `executable_but_failing` (realized but not yet proven passing), `passing`, `stagnated`, `escalated`, and `manual_pending` as first-class values. A newly complete static realization becomes `executable_but_failing`, never `passing`. Existing passing/stagnated/escalated runtime states survive a dry refresh while infrastructure remains present; removing required infrastructure returns an automated case to `unrealized`. Manual cases always become non-blocking `manual_pending`.
- Formal prompt-context loading performs the dry check after manifest/specification integrity validation, updates only the mutable `job_verification_states.status` rows, reloads those rows, and adds the realization details to the runtime summary. State changes receive an audit event. No migration was required because the additive Milestone 4 state table already owns aggregate status. Canonical manifest JSON, canonical/artifact hashes, versioned artifacts, and history are never rewritten.
- `refresh_job_realization` provides the same frontend-neutral service path and explicitly returns `None` for Quick Goal. It verifies that Quick Goal has no manifest/state side effects. Repeated formal loads round-trip the state, and persistence tests verify immutable manifest bytes and hashes remain unchanged.
- Formal PLAN and REVIEW prompts expose exact missing infrastructure and prioritize a focused verification-infrastructure task. Post-schema semantic validation rejects formal `DONE` while any automated case is unrealized and requires the next `CONTINUE`/`REPAIR` task to carry one of the affected verification IDs. This validation runs inside the existing bounded Claude, Codex, and Gemini decision-remake path. Manual pending cases do not block `DONE`. Quick Goal calls continue through the unchanged prompt and decision branches without a manifest, realization scan, state, or formal ID requirement.
- The formal worker prompt now requires the structured case marker or equivalent adapter result and explicitly states that a broad successful test command does not realize the intended case.
